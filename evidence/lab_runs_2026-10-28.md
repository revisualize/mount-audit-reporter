The released `mount_audit_reporter.sh` (sha256 beginning `2778d1c629cb`, commit `020992b`) was run on a lab client against a real NFS server and a real Samba server: 20 audits in all. For 17 of them, the expected exit code was written into the script beforehand, from what the README and the project page say, and all 17 matched. The other 3 recorded how an SMB mount reads back, a question the README left open before these runs.

## NFS: 13 audits, 13 matched

The export was mounted four ways, and each mount was audited against two manifests: one that requires `hard`, and one that forbids `soft`.

| Mount command | Option string reports | Require `hard` | Forbid `soft` |
|---|---|---|---|
| `mount -t nfs4` with no recovery option | `hard` | exit 0 | exit 0 |
| `-o hard` | `hard` | exit 0 | exit 0 |
| `-o soft` | `soft` | exit 1, `required option missing: hard` | exit 1, `forbidden option present: soft` |
| `-o softerr` | `softerr,softreval` | exit 1, `required option missing: hard` | exit 0 |

The last row is the case the README warns about: a rule that forbids `soft` passes a `softerr` mount, and a rule that requires `hard` catches it. On this 7.0.0 client, a mount given no recovery option reported `hard`, the behavior the README describes from the Linux 6.18 source.

Five more audits, the last four with the export mounted `hard` underneath:

| Arrangement | Result |
|---|---|
| Nothing mounted yet (run first) | exit 1, `not mounted` |
| Manifest names `192.168.77.99` as the server | exit 1, `source is 192.168.77.10:/srv/nfs/projects, expected 192.168.77.99:/srv/nfs/projects` |

## SMB: 7 audits, 4 predicted and matched, 3 recorded

| Mount command | Manifest | Result |
|---|---|---|
| (nothing mounted) | `cifs ro rw //192.168.77.10/archive` | exit 1, `not mounted`, as predicted |
| `-t cifs -o vers=3.1.1,ro` | `cifs ro rw //192.168.77.10/archive` (the README's example shape) | exit 0, as predicted |
| `-t cifs -o vers=3.1.1,ro` | same, naming the share `//192.168.77.10/other` | exit 1, source finding, as predicted |
| `-t cifs -o vers=3.1.1,rw` | `cifs ro rw //192.168.77.10/archive` | exit 1, `required option missing: ro` and `forbidden option present: rw`, as predicted |
| `-t cifs -o vers=3.1.1,ro` | `cifs vers=3.1.1 -` | exit 0, recorded |
| `-t smb3 -o ro` | `cifs ro rw //192.168.77.10/archive` | exit 1, `fstype is smb3, expected cifs`, recorded |
| `-t smb3 -o ro` | `smb3 ro rw //192.168.77.10/archive` | exit 0, recorded |

What the SMB mounts showed:

- A share mounted with `-t smb3` reports the filesystem type `smb3`, and one mounted with `-t cifs` reports `cifs`. A manifest has to use the type that mount reports; generate mode prints it.
- Every SMB mount reported `soft`, although none was mounted with it. mount.cifs(8) documents `soft` as the default for CIFS. None of these mounts used `hard`, so how a `hard` SMB mount reads back is still unobserved.
- The option string includes `username=labsmb`, so a manifest made by generate mode names the account. The password never appeared in it on any of the three mounts.
- Each SMB mount listed 26 options. The mount command named `credentials=`, `vers=3.1.1`, and `ro` or `rw`; everything else came from the credentials file, mount.cifs, or the kernel. Each NFS mount listed 15 or 16, including `fatal_neterrors=none`, which nobody typed. That is why a generated manifest needs pruning before use.

## Limits of these runs

- One NFS server, one Samba server, one client, one kernel. A different kernel can report options differently; regenerate and review the manifest after a kernel upgrade.
- No server went away during a run, so nothing here shows how the audit behaves against a hung `hard` mount.
- No Windows file server was used; the SMB server was Samba.
- The audit ran by hand, once per arrangement, and not under cron or for a sustained period.

## Reproducing the runs

The scripts assume the lab layout above: a server at 192.168.77.10 with the two exports and the `archive` share, a client user with passwordless sudo, and the mount points under `/mnt/lab`. On the client, as that user:

```sh
bash nfs_lab_audit_client.sh
bash smb_lab_audit_client.sh
```

The SMB scripts read the Samba account from `/home/lab/smb_lab_credentials`, a file of `username=` and `password=` lines. Run `smb_lab_server_setup.sh` with sudo on the server first. Each client script unmounts everything it mounted before it exits, including after a failure.
